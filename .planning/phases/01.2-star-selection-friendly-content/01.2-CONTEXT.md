# Phase 1.2: GitHub-Star Selection & Friendly Content - Context

**Gathered:** 2026-11-03 (owner request after reviewing the first v2 preview, run 41409445829)
**Status:** Ready for planning

<domain>
## Phase Boundary

The pipeline built in Phases 1 and 1.1 changes in four ways: how papers are picked (GitHub stars with a variable count), where images go (per article, none under the headline), which model-info rows show (no `확인 필요` rows), and how Claude writes (friendly 해요체 for non-specialists, plus a one-line use idea).

Unchanged: the ISO Mon–Sun KST week, the Monday 08:00 KST send (Phase 5), the Figma v2 layout and otters, delivery, and the hard rule that facts come from code.

</domain>

<decisions>
## Implementation Decisions

### Week and send day
- **D-01:** The week stays the HF / ISO week, Mon–Sun KST, same as HF's weekly page (`week/2026-W44`). The issue for 10/26 (Mon)–11/1 (Sun) is sent on Monday 11/2. The owner's "nov 1-7" example was approximate; the owner confirmed HF's Mon–Sun. No change to COLL-01.

### Selection (COLL-05)
- **D-02:** Rank the week's papers by GitHub stars of their linked repo. The researcher decides the source: HF paper data may already carry the star count (verify the field), otherwise use the GitHub API with the Actions `GITHUB_TOKEN`. Stars are the total at fetch time. This replaces the upvote ranking.
- **D-03:** Count rule: N = number of papers with ≥ 100 stars, capped at 10. If N < 3, take the 3 most-starred papers anyway. If fewer than 3 papers have a repo at all, fill the remaining slots by HF upvotes. Ties break by upvotes, then by comments.
- **D-04:** "Top 10" wording becomes N-aware everywhere. The Top 3 section always shows ranks 1–3. The "4위부터 {N}위까지" section appears only when N > 3.

### Headline and greeting
- **D-05:** Headline: "{emoji} {hook} 이번 주 AI 모델 {N}", for example "🤖 말을 알아듣고 로봇이 움직인다? 이번 주 AI 모델 10".
- **D-06:** Greeting (owner chose the star-based wording): "구독자님, 안녕하세요. 지난주 Hugging Face Papers에 올라온 모델 중 GitHub star를 많이 받은 {N}개를 골랐어요!" Personalized sends use "{name}님". The text follows the owner's own example sentence.
- **D-07:** No image under the headline. Remove the hero image; the otter top banner stays. Supersedes Phase 1.1 D-18.

### Per-article images (DSGN-08)
- **D-08:** Each article shows its own image at the top of its card when one exists. Source order: HF `paper.mediaUrls` image first, else the first image in the repo's GitHub README (absolute https, PNG/JPEG/GIF only, skip badges/shields and SVG). Card 1 no longer skips its image, since there is no hero.
- **D-09:** The allowed image hosts widen from HF CDN only to also include GitHub README image hosts (the researcher lists them, e.g. raw.githubusercontent.com, user-images/private-user-images). Images are still never embedded. Width/height come from the image header. Large images (the 590 KB HF PNG seen in the preview) need a size policy; the researcher proposes one, for example skipping over a byte cap or relying on display width.

### Model info rows
- **D-10:** Omit any 모델 정보 row whose value is `확인 필요`. If all five are unknown, drop the whole box. The schema keeps `확인 필요` as the stored value; only rendering changes.

### Tone and content (ANLY-09, ANLY-10)
- **D-11:** All Claude-written text uses friendly 해요체, like "…골랐어요!" and "…해주는 모델이에요." No 반말 or 하다체 ("제안했다", "모델이다"); the first preview used them and the owner wants them gone. The rules are added to the prompt, with a code-side check (sentence endings) that retries once.
- **D-12:** Explain what the model is so a non-specialist understands, and keep technical terms in English (D-04/D-05 of Phase 1 still apply). The one-line summary plus the three lines should read like a friendly explanation, not an abstract.
- **D-13:** Bring back one line of 활용 아이디어 per article, grounded in the paper or project page (Phase 1 D-07 style: plain "where it could be used", not creative). This is a schema change: a new single `use_idea_ko` field, with `use_ideas_ko` list staying removed. — **Reversibility:** one-way — it changes the frozen `Issue` v2 contract, so it needs a v3 snapshot and a checkpoint before committing it.
- **D-14:** Fix the stray "()" seen in a 구조 value (e.g. "…행동 조건화 ()"): strip empty brackets in code.

### Decisions after research (2026-11-03)
- **D-15:** Star source is HF `paper.githubStars` (already fetched; 145/214 W44 papers carry it). No GitHub API or token in the primary path. The GitHub API with `github.token` is only a documented fallback.
- **D-16:** Headline hook keeps the headline style from the owner's example ("…움직인다?") and is exempt from the 해요체 check. All body text (greeting, summaries, lines, model info prose, use idea) must be 해요체.
- **D-17:** Card meta shows `★ {stars}` (thousands separator) for star-ranked items. Upvote-filled items (D-03 top-up) show `▲ {upvotes}`.
- **D-18:** README images: only hosts that serve directly without redirects (`cdn-uploads.huggingface.co`, `raw.githubusercontent.com`). PNG/JPEG/GIF, ≥ 576 px wide, aspect 1.2-4.0, ≤ 1 MB. Skip logo/badge-like names, and skip `github.com/user-attachments` (302 to an expiring S3 URL). Expected coverage ≈ 4/10.
- **D-19:** If text is still not 해요체 after the one retry, log a warning and send anyway (not fatal).
- **D-20:** Replace the `prompts/humanizer_ko.md` rule that asks for "~한다" endings (the root cause of the 하다체 preview) with 해요체 rules.
- **D-21:** With N between 4 and 10 the rest section title reads "놓치기 아까운 4위부터 {N}위까지 👀". With N == 4 it reads "놓치기 아까운 4위 👀". With N == 3 the section is skipped.
- **D-22:** Put the one-line 활용 아이디어 inside the existing summary cell (size budget: a separate row would leave about 1 KB of headroom).

- **D-23 (owner, after the 1.2 preview run 41557111749):** ranks 1-3 had no image. Add a third image source: the first figures of the paper's arXiv HTML page (`https://arxiv.org/html/{id}`, no redirect; only images under the paper's own versioned dir, at most 2 candidates, same D-18 size and ratio rules). Order: HF media, then README, then arXiv. `ARXIV_IMAGE_HOST` joins the ItemImage host allowlist; this is a validator change only, and the v3 JSON snapshot does not change. On W44 the card image coverage goes from 4/10 to 8/10.

### Claude's Discretion
- Exact star-source endpoint, rate-limit handling, cache, and the README image parsing rules.
- Card layout tweak for the one-line 활용 아이디어 (position and label).
- Whether to bump the schema to v3 or extend v2 additively (must follow the one-way checkpoint either way).

</decisions>
